# FiberSocial — Project Instructions

## Git Workflow

- **Never push directly to `main`.** All changes — including documentation, formatting, or one-line fixes — must go through a feature branch and a pull request.
- **Never edit files in the primary checkout to start new work — always create an isolated worktree first.** Before touching any file, run `git worktree add ../FiberSocial-<slug> -b <type>/<slug>` and do the work there. This isn't optional even for "just config" changes: the primary checkout routinely has in-progress uncommitted edits sitting in it, and editing in place mixes unrelated changes into the same diff, making it impossible to cut a clean single-purpose PR without dragging along someone else's WIP (or reverting it by accident).
- **Never merge a PR yourself.** After creating or updating a PR, hand the URL to the user and wait. Never run `gh pr merge` or any equivalent.
- Branch naming: `feat/`, `fix/`, `chore/`, `docs/` prefixes matching the commit type.

## Secrets

- Never commit `ravelry.client_secret`. It lives in the gitignored `local.properties` as `ravelry.client_secret` for local builds, and in the `RAVELRY_CLIENT_SECRET` GitHub Actions repo secret for CI builds (`android-build.yml` and `release-android.yml` materialize it into CI's own `local.properties` — those injections are sanctioned, not leaks).
- **`android-build.yml` injects the Ravelry credentials only on post-merge pushes to `main`, never on pull-request runs** (the `github.event_name == 'push' && github.ref == 'refs/heads/main'` ternary on the "Write local.properties" step; issue #266). This repo is public and Actions artifacts on a public repo are downloadable by anyone, so a PR-run APK with the real secret baked into `BuildConfig` published it to the world on every branch push. PR artifacts now build with blank credentials — they compile and install fine but fail login with `invalid_client`, exactly like fork-PR artifacts always have. **To smoke-test login from a CI artifact, use an `app-debug`/`app-release` artifact from a `main` run, not a PR run.**
- Residual, accepted exposure: `main`-run artifacts and every public GitHub Release APK still contain the real secret, because a client secret shipped in a mobile binary is always extractable — that part is inherent to native OAuth apps, not a CI bug. The gate removes the incidental per-PR exposure, not the inherent one. Closing the remainder would mean a dedicated, rotatable CI Ravelry app (deliberately not done — see #266). Treat the current secret as already-disclosed and rotate it if Ravelry ever supports doing so.
- Same pattern for release signing: the keystore and its passwords live in `local.properties`/a gitignored keystore file locally, and in the `RELEASE_KEYSTORE_BASE64`, `RELEASE_KEYSTORE_PASSWORD`, `RELEASE_KEY_ALIAS`, `RELEASE_KEY_PASSWORD` GitHub Actions repo secrets for CI (`android-build.yml` decodes the base64 secret back into a keystore file and writes the rest into CI's `local.properties`). Unlike the Ravelry secrets, these are optional in `android-build.yml` — CI skips release signing/build entirely (not a failure) when `RELEASE_KEYSTORE_BASE64` isn't set. The tag-triggered `release-android.yml` does the same materialization but treats all of these as required, failing loudly if any is missing.
- iOS release signing follows the same shape, one level more involved because App Store distribution needs a certificate *and* a provisioning profile *and* a non-interactive way to upload (Apple ID + password can't get past 2FA in CI). Required repo secrets: `IOS_DIST_CERTIFICATE_BASE64` (base64 of an **Apple Distribution** `.p12`, not "Apple Development" — the wrong cert type for App Store upload) + `IOS_DIST_CERTIFICATE_PASSWORD`, `IOS_PROVISIONING_PROFILE_BASE64` (base64 of the App Store distribution `.mobileprovision` for `com.myhobbyislearning.fibersocial`), and `IOS_ASC_API_KEY_BASE64` + `IOS_ASC_KEY_ID` + `IOS_ASC_ISSUER_ID` (an App Store Connect API key — Users and Access → Integrations — with at least App Manager role; this is what authenticates the upload instead of an Apple ID/password). One more piece, `APPLE_TEAM_ID`, is a repo **variable** (`vars.APPLE_TEAM_ID`), not a secret — it isn't sensitive, it's embedded in every signed binary regardless. `release-ios.yml`'s `build-rc` job imports the cert into a job-scoped temporary keychain (never the runner's login keychain) and treats all of these as required, same fail-loudly behavior as the Android release secrets. Locally, none of this is needed — a dev's own Xcode "Automatically manage signing" handles signing with their personal team, which is why `DEVELOPMENT_TEAM`/`CODE_SIGN_IDENTITY`/`PROVISIONING_PROFILE_SPECIFIER` should never be committed to `project.pbxproj` (Xcode injects them locally; CI passes its own values as command-line build-setting overrides instead, so the committed project file stays signing-identity-agnostic for every other contributor).
- **Release-candidate QA/promotion pipeline** (issue #265, both platforms now) needs several pieces set up manually before the release workflows can run end to end:
  - `PLAY_SERVICE_ACCOUNT_JSON` (repo secret): a Play Console service-account JSON key (Play Console → Setup → API access) with permission to manage testing tracks and production releases for `com.myhobbyislearning.fibersocial`. Used by `release-android.yml`'s both jobs via `r0adkll/upload-google-play`.
  - `PLAY_TESTING_TRACK` (repo **variable**): the exact Play Console track alias release candidates get pushed to for QA (confirm the real alias for the existing closed test — issue #320 — in Play Console rather than assuming; commonly `internal` or a custom closed-track name).
  - Two new GitHub **Environments** (Settings → Environments): `android-release` and `ios-release`, each with "Required reviewers" turned on. This is the actual manual-QA gate — the `promote` job in each workflow pauses until an approved reviewer signs off in the Actions UI, after running the relevant QA checklist (`docs/android-release-qa-checklist.md` / `docs/ios-device-checklist.md`) against the release candidate. (Precedent for the `environment:` key already in this repo: `pages.yml`'s `github-pages` environment.)
  - QA testers reaching each iOS release candidate on TestFlight needs no CI step at all: the QA Internal Testing group is configured in App Store Connect (Internal Testing group settings → "Automatic distribution") to auto-add every new build. CI previously tried to do this explicitly via `fastlane pilot`, but pilot's group-assignment call is unreliable for manually-managed internal groups (a still-open fastlane/Apple API bug, fastlane/fastlane#22051) and is redundant with automatic distribution anyway — removed rather than worked around further.
- `ios-debug-build.yml` (see `docs/ios-debug-builds.md`) needs one more secret beyond the above: `IOS_ADHOC_PROVISIONING_PROFILE_BASE64`, an **Ad Hoc** (not App Store) provisioning profile scoped to specific registered devices. It reuses the same `IOS_DIST_CERTIFICATE_*`/`APPLE_TEAM_ID`/Ravelry secrets as `release-ios.yml` — Ad Hoc profiles are signed with the same Distribution certificate, just device-limited, so no new certificate is needed, only a new profile. That profile has to cover the bundle id of the configuration being built, and those now differ (`…fibersocial.debug` for Debug, `…fibersocial` for Release — see "Debug builds install alongside the store build" below): one **wildcard** profile (`com.myhobbyislearning.*`) covers both, or put a second explicit-App-ID profile in the optional `IOS_ADHOC_DEBUG_PROVISIONING_PROFILE_BASE64` secret and the workflow picks whichever matches.

## Debug builds install alongside the store build

- **A debug build is its own app on the device, not a replacement for the published one** — both can be installed at once, and they share nothing. Android does it with `applicationIdSuffix = ".debug"` (`app/build.gradle.kts`), iOS with a Debug-configuration `PRODUCT_BUNDLE_IDENTIFIER` of `com.myhobbyislearning.fibersocial.debug` (`project.pbxproj`).
- **Data isolation comes from the id itself, on both platforms** — there is no second mechanism to keep in sync. Android scopes every per-app store to the applicationId (`/data/data/<id>`: the plain and encrypted SharedPreferences files, the Tink keyset, WorkManager's database, notification channels, permission grants); iOS scopes the container, `NSUserDefaults.standardUserDefaults` and the default keychain access group to the bundle id. Consequence to expect when testing: **the debug build needs its own Ravelry login**, and starts with empty group order/notification state.
- Both are labelled "FiberSocial Debug" and carry a dark app icon (near-black `#121212` behind a light-purple mark) instead of the lavender release icon, so the two are distinguishable on a home screen. Sources: Android `app/src/debug/res/` (overrides `ic_launcher_background` and the `ic_launcher_foreground.png` layers), iOS `Assets.xcassets/AppIconDebug.appiconset`. Both render from `docs/design/logo/FiberSocialLogo_darkmode.svg` via `scripts/generate_launcher_icons.py` — don't hand-edit the PNGs.
- Nothing in the app hard-codes its own package/bundle id, which is what makes the split safe: the OAuth redirect (`fibersocial://auth/callback`) is intercepted inside the login WebView rather than by an intent-filter or a registered URL scheme, and Android's notification deep links are explicit-component PendingIntents. The two places that did name it are now derived — iOS's `BGTaskSchedulerPermittedIdentifiers` (`$(PRODUCT_BUNDLE_IDENTIFIER).refresh`) and `EventSync.REFRESH_TASK_IDENTIFIER` (built from `NSBundle.mainBundle.bundleIdentifier`), which must keep agreeing or `BGTaskScheduler` refuses the registration. Android's `namespace` is deliberately NOT suffixed — it names the Kotlin/`R`/`BuildConfig` package, not the install identity.
- Migration trap on Android: a debug build made *before* the suffix is installed under the release package. `deploy.sh` detects that (a DEBUGGABLE build under `com.myhobbyislearning.fibersocial`) and uninstalls it, on either path — left in place it would both shadow the real app on the home screen and block a Play install.

## Building & running the Android app

- `local.properties` is gitignored, so a fresh `git worktree add` checkout won't have it. Copy it from an existing checkout (`src/platform/android/local.properties`) before building, or OAuth login will fail with `invalid_client` (empty `ravelry.client_id`/`ravelry.client_secret`).
- `RAVELRY_CLIENT_ID`/`RAVELRY_CLIENT_SECRET` are `BuildConfig` fields generated from `local.properties`. Because they're compile-time-constant `String`s, Kotlin inlines their value into every call site at compile time — if you add/fix `local.properties` *after* an earlier build already ran without it, a plain `./gradlew assembleDebug` can report everything as `UP-TO-DATE` and skip recompiling those call sites, silently keeping the stale (empty) inlined value even though the generated `BuildConfig.java` itself looks correct. If auth fails with an empty `client_id` despite correct `local.properties`, run `./gradlew clean` before rebuilding.
- A corrupted on-device `EncryptedSharedPreferences` keyset (`AndroidKeysetManager`/Tink errors, e.g. `InvalidProtocolBufferException: Protocol message contained an invalid tag` — can happen after an uninstall/reinstall cycle) is self-healed by the app since `encryptedKeyValueStore` gained recovery: it wipes the unreadable prefs file and recreates it, so instead of crashing on launch the app just asks the user to log in again. If a build predating that fix crashes this way, recover manually with `adb shell pm clear com.myhobbyislearning.fibersocial`. (After a debug↔release build-type switch `deploy.sh` uninstalls the old build; the reinstall then self-heals on next launch, so it no longer needs a `pm clear` step.)

## Building & running the iOS app

- The Xcode project is `src/platform/ios/FiberSocial.xcodeproj`; its "Build ComposeApp framework" phase runs `./gradlew :composeApp:embedAndSignAppleFrameworkForXcode` in `src/platform/android`, so Kotlin changes rebuild automatically. The script validates JDK candidates by major version (an inherited `JAVA_HOME` may point at an old JDK; it probes `java_home -v 17` and homebrew's `openjdk@17` as fallbacks).
- Secrets mirror Android's `local.properties`: put `RAVELRY_CLIENT_ID`/`RAVELRY_CLIENT_SECRET` in the gitignored `src/platform/ios/Config.local.xcconfig` (`Config.xcconfig` holds empty committed defaults and optionally includes it). Without them the app runs but login fails with `invalid_client`, with a launch-time warning.
- Simulator build/test from the CLI: `xcodebuild -project FiberSocial.xcodeproj -scheme FiberSocial -destination 'platform=iOS Simulator,name=iPhone 17' build` (or `test` — the hosted XCTests cover the Keychain/NSUserDefaults stores; the bare Kotlin/Native test runner has no keychain daemon, so `:composeApp:iosSimulatorArm64Test` keychain write tests skip themselves there by design).
- Feature-complete vs Android (#119): device photo uploads via PHPicker (HEIC transcodes to JPEG on upload), app icon, platform-aware settings copy. Notifications (#118): reminders are OS-scheduled local notifications; new-event polling is a sync on every foreground activation plus opportunistic `BGAppRefreshTask` (needs a real device to observe — the simulator rejects background-task submission, logged and harmless). TestFlight steps: src/platform/ios/README.md; device verification: docs/ios-device-checklist.md.

## Release builds

- `./gradlew assembleRelease` (or `./deploy.sh --release`) needs a signing keystore, configured the same way as the Ravelry secrets: gitignored, read from `local.properties` at build time. `app/build.gradle.kts` only creates the `release` signing config if `release.store.file` is set, so builds without it stay unsigned rather than failing.
- `./gradlew bundleRelease` builds the Android App Bundle (`.aab`) Play Console requires for store submissions — `deploy.sh`/direct-install users still want the APK from `assembleRelease`. It shares the same `release` signing config and `local.properties` keys automatically (the Android application plugin wires `bundleRelease` to whatever `signingConfig` is set on the `release` buildType); no separate configuration exists for it. Output: `app/build/outputs/bundle/release/app-release.aab`.
- Required `local.properties` keys: `release.store.file` (path relative to `src/platform/android/`), `release.store.password`, `release.key.alias`, `release.key.password`.
- The actual keystore file (`*.keystore`/`*.jks`, gitignored) doesn't come along with `git worktree add` any more than `local.properties` does — copy it into a fresh worktree from an existing checkout alongside `local.properties`, don't regenerate it (a new keystore produces a different signature and can't upgrade-install over an app signed by the old one).
- CI (`android-build.yml`) builds and uploads a signed `app-release` artifact on every push/PR too, once the `RELEASE_KEYSTORE_BASE64` repo secret (and its companion password/alias secrets) are set — see the Secrets section above. This is only a transient (7-day) Actions artifact for early smoke-testing, not a public release — see "Versioning & cutting a release" below for that.

## Versioning & cutting a release

- Versioning is manual, not automatic per-commit: pick a `MAJOR.MINOR.PATCH` version, then run `scripts/release.sh <version>` (e.g. `scripts/release.sh 1.2.0`) from `main` with a clean working tree, up to date with `origin/main`. It tags the current commit `vMAJOR.MINOR.PATCH` and pushes the tag.
- **A tag push no longer goes straight to public on either platform.** Each builds a release candidate that needs a human to run manual QA and approve it before it's live — see #265 (the tag-triggered workflow used to publish without ever re-running the unit-test suites). The flow, run independently per platform (`.github/workflows/release-android.yml` and `.github/workflows/release-ios.yml`, each with its own `concurrency` group so one platform's runner speed doesn't block the other):
  1. **`build-rc` job**: verifies the tag is on `main` and resolves unambiguously, checks the module-collision gate (Android only), **runs the automated test suites against this exact commit** (the actual fix for #265 — a test failure blocks the candidate outright), then builds and signs the release artifacts.
  2. Publishes the release candidate somewhere a human can install it: Android gets a GitHub Release marked `--prerelease` (not `--latest`, so the public download link doesn't move yet) plus an upload to the Play Console `PLAY_TESTING_TRACK` testing track; iOS uploads to App Store Connect (TestFlight internal, as before), from where QA testers get it automatically — the QA Internal Testing group auto-distributes every new build, so no extra CI step is needed (and none is attempted; the explicit `fastlane pilot` group-assignment was removed as unreliable for manually-managed internal groups, a still-open fastlane/Apple bug).
  3. A human runs manual QA against that candidate build using `docs/android-release-qa-checklist.md` / `docs/ios-device-checklist.md`.
  4. **`promote` job**: gated on the `android-release` / `ios-release` GitHub Environment (required reviewers) — the job sits paused in the Actions UI until an approved reviewer clicks Approve. On approval:
     - Android: re-pushes the *exact same already-tested* AAB (downloaded from the `build-rc` job's artifact, not rebuilt) to the Play Console `production` track, and flips the GitHub Release from prerelease to `--latest` — this is what moves the public download link.
     - iOS: Apple review can't be triggered via API, so this job doesn't touch App Store Connect — it's an audited approval checkpoint whose job summary reminds you to go submit the already-uploaded build for App Store review by hand.
  - If QA finds a bug, don't try to patch the candidate in place — reject the approval, fix the bug, and cut a new patch version (a fresh tag) that goes through the same pipeline.
- `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` for iOS are derived from the tag using the same `MAJOR * 1_000_000 + MINOR * 1_000 + PATCH` packing as Android's `versionCode`, so both platforms' build numbers stay in the same scheme and (per TestFlight's requirement) strictly increase release-over-release. `release-ios.yml` also accepts a manual `workflow_dispatch` run (no tag needed) to dry-run its `build-rc` job in isolation — that path uses `0.0.0` as the marketing version — the one value `scripts/release.sh` explicitly rejects, so it can never collide with a real release — with the CI run number as the build number, so repeat dry runs don't collide with each other either.
- `app/build.gradle.kts` derives `versionName`/`versionCode` from the tag when the current commit is exactly on one (`git describe --tags --exact-match --match 'v[0-9]*.[0-9]*.[0-9]*'`): `versionName = "MAJOR.MINOR.PATCH"`, `versionCode = MAJOR * 1_000_000 + MINOR * 1_000 + PATCH`. This needs to strictly increase release-over-release for in-place upgrade installs (tapping a newly downloaded APK) to work — don't tag a lower version after a higher one has shipped. Ordinary (non-tagged) builds are unaffected: they keep the existing git-hash `versionName` and `versionCode = 1`. One local trap: the derivation keys off the *commit*, not the build type, so even a debug `deploy.sh` build made while HEAD sits on a release tag gets the big tag-derived `versionCode` — the next dev build (back to `versionCode = 1`) is then an install "downgrade", which is why `deploy.sh` passes `adb install -d`.
- The public download link is always `https://github.com/torrey1028/FiberSocial/releases/latest/download/app-release.apk` — GitHub resolves `releases/latest` to whichever release was most recently marked latest, so this automatically follows whatever tag was most recently **promoted** (not just tagged and pushed — see above). It does not update on every push to `main`, nor at RC-publish time — only when the `promote` job flips it.

## Logging

- Use `println("FiberSocial: ...")` for debug logging in common module code (visible in logcat as `System.out` tag).
- **Login-flow diagnostics go through `DebugLog.log(...)` instead** (it tees to the same `println` prefix AND an in-memory buffer a debug build can export via a share sheet — the only way to get evidence off an OTA-installed iPhone). A login-adjacent line written with bare `println` appears in logcat but is silently missing from the exported device trace.
- Never interpolate a session cookie into any log call — route it through `describeSessionCookie` (issue #395); URLs in login-flow lines go through `describeUrlForLog`.
- Rely on logcat for debugging — do not use screenshots as a substitute.
